# Аудит интерфейса и бизнес-логики «в браузере» — 2026-10-04

Сессия S48. Первый проход, где проект проверяли **не глазами по коду, а вживую**:
headless-Chromium обошёл каждую страницу в каждой из 7 ролей и нажал каждую кнопку.

Стек проверки: Playwright 1.49.1 + Chromium 131, прод-сборка `frontend/dist` за
nginx-подобным статик-сервером (тот же same-origin, что в проде). Ошибки консоли,
ответы 4xx/5xx и горизонтальное переполнение собирались на каждой странице.

## 2. Что исправлено

### 2.1. Публичные страницы «Доставка» и «О нас» были пустыми — **главный дефект**

Оба пункта висят в основном меню витрины, но `CmsPageView` получал 404 и показывал
«Раздел готовится к публикации». То есть **два из шести пунктов меню у каждого
посетителя выглядели как недоделка**.

Новая миграция `V26__seed_cms_pages.sql` заводит обе статьи в `articles` со статусом
`PUBLISHED`: сроки и стоимость доставки, самовывоз, условия для юрлиц, история
компании, принцип работы, «почему это важно». Дальше контент правится в админке
(«Админка → Страницы») — сид только заполняет стартовое наполнение.

Идемпотентно: `ON CONFLICT (slug) DO NOTHING`, чтобы правки администратора не затирались
при повторном прогоне.

> Побочно: `DeliveryPage.tsx`, `AboutPage.tsx` и `ManagerDashboardPage.tsx` оказались
> мёртвым кодом — их заменил `CmsPageView` в S37, но файлы остались и вводили в
> заблуждение (у доставки был готовый текст, который просто не показывался). Удалены.

### 2.2. Гость получал 401 в консоли на каждой публичной странице

`AuthInit` при старте всегда звал `POST /auth/refresh`. У анонимного посетителя
refresh-токена нет и не будет — запрос заведомо проваливался: лишний round-trip и
красная ошибка в консоли на каждой странице.

Refresh-токен в httpOnly-куке, JS его не видит. Поэтому добавлен remember-флаг в
`localStorage` (`gusto.session`): он ставится при входе и снимается при выходе.
Гость (ни входа, ни флага) уходит сразу в анонимный режим. Если флаг есть, а куки
уже нет — refresh попробуется и молча провалится, как раньше.

### 2.3. Тап-таргеты (WCAG 2.5.5 / 2.5.8)

Замерялись на 375px — там WCAG 2.5.5 и имеет силу (для мышиного курсора на десктопе
44px не требуются, поэтому правки ограничены тач-ширинами).

Было 27 элементов меньше 44px на главной, стало 5. Исправлено:

| Элемент | Было | Стало |
|---|---|---|
| Ссылки футера | 20px | 44px |
| Ссылка «Политика конфиденциальности» | 17px | 44px |
| «Войти» в шапке | 41×21 | 44px по высоте |
| «Все товары →», «Перейти в каталог →» | 20px | 44px |
| Кнопки `size="sm"` («В корзину», «Корзина») | 32–33px | 44px |
| Название товара в карточке | 26px | 44px |
| Бургер «Меню» и пункты меню бэк-офиса | 28–33px | 44px |

### 2.4. Кегль полей ввода на телефоне (iOS zoom)

У `Input` был мобильный bump до 16px (закрыт в S44), а у `Select` и `Textarea` —
нет. На iOS фокус поля меньше 16px зумит страницу, и пользователь теряет строку,
на которой печатал. Именно на выпадающих списках и текстовых полях: комментарий
к заказу, заявка с «Стать клиентом», фильтры каталога.

Добавлен тот же bump для обоих компонентов + варианты списка `Select` до 44px по высоте.

### 2.5. Порядок заголовков (WCAG 1.3.1)

- Футер использовал `<h4>` сразу после заголовков страницы — `h1 → h4` и `h2 → h4`.
  Заменено на `<h2>`.
- `Card` жёстко рендерил заголовок как `<h3>`. На дашбордах карточка идёт сразу за
  `<h1>` страницы, то есть `h1 → h3`. Добавлен проп `titleAs`, на дашбордах —
  `titleAs="h2"`.

### 2.6. Градиенты (бренд-книга §1.7)

Четыре места использовали `linear-gradient` поверх брендовых цветов: плейсхолдер
на главной, подложка фото категорий, плейсхолдер карточки товара, плейсхолдер
страницы товара. Заменены плоскими заливками того же тона.

### 2.7. Переполнение корзины на 375px

Кнопки «Оформить заказ» и «Очистить» стояли в ряд без переноса и выдавливали
правую за край экрана на 4px (WCAG 1.4.10, reflow). Добавлен `flex-wrap: wrap`.

## 3. Демо-данные: V25 и его цена

`V25__demo_business_data.sql` (из предыдущей сессии) закрывает главный пробел
демо-стенда: **в базе не было ни одного бухгалтера и ни одного менеджера**, поэтому
кабинет бухгалтера, CRM и склад было физически невозможно открыть — а значит,
и проверить, и починить. Добавлены роли, две компании, клиенты, скидки, персональные
цены, заказы во всех статусах, счёт с частичной оплатой, ТТН, лиды по всей воронке,
CRM-задачи, поставщики и заказ поставщику.

### Побочный эффект: 25 упавших тестов — и что с этим сделано

Сид-миграции заливают демо-данные **во все интеграционные тесты**, потому что
тесты готовились к Flyway-базе, а не к Flyway+демо. Первый прогон:
`Tests run: 139, Failures: 2, Errors: 25` — `DataIntegrityViolation` в `delete from
products`, потому что сид-заказы висели на `order_items`.

Ручные цепочки `repository.deleteAll()` в каждом тесте — хрупкие: они перечисляют
таблицы, о которых тест знает, и ломаются на каждой новой сид-миграции.

**Решение:** `by.gusto.support.DatabaseCleaner` — `TRUNCATE ... RESTART IDENTITY
CASCADE` по рабочим таблицам, кроме мастер-данных. Порядок зависимостей знать не
нужно, и будущая миграция уже не сломает подготовку теста. Подключён во **всех 31**
интеграционных тестах.

Три грабли, на которые наступили по дороге (все три — следствие того, что чистка
идёт по всей схеме, а не по списку таблиц теста):

1. **CASCADE не уважает KEEP.** `users` стоял в списке исключений, но `companies`
   туда тоже надо: `TRUNCATE companies CASCADE` сносит и `users`, потому что
   ссылка `users.company_id → companies` идёт именно в эту сторону. Половина
   тестов логинится как сиед-админ из V2 и молча получала 401.
2. **Мастер-данные тоже нужны.** `products`, `categories`, `product_prices`,
   `stock_balances`, `stock_movements` заводят V6/V9 — тесты читают их по SKU
   (`findById(...)`, «начальный приход отражён в журнале»). Чистить их нельзя.
3. **Цикл FK.** `users.company_id ↔ companies.manager_id` — удалить нельзя ни
   так, ни эдак, пока ссылки живы. Чистка сначала зануляет обе стороны, потом
   удаляет.

Итог: `mvn -B verify` — **139 тестов, 0 failures, 0 errors**. Фронт: vitest 108,
eslint 0 ошибок, прод-сборка собрана.

## 4. Что осталось (не чинил осознанно)

| Что | Почему |
|---|---|
| **Нет UI прайс-листов и цен** | `AdminPricingController` — 20 эндпоинтов, ноль экранов. Это отдельная фича (план S-блок про прайсы), не дефект. Кабинет клиента показывает цены из витрины, персональные — бэкенд считает, но ручного редактора нет. |
| **Нет UI платежей** | `PaymentIntegrationTest` покрывает API; экрана приёма оплаты нет. |
| **Пропаганда-мёртвый бандл 902 kB** | Vite предупреждает. Кода-спилтинга нет: один чанк на всё приложение. Первая загрузка витрины тяжеловата для мобильного интернета. |
| **Единый чанк без разделения по зонам** | То же. |
| **Две вкладки при входе** | Refresh-токен ротируется, reuse-detection отзывает «повторно использованный». Две вкладки, открытые одновременно сразу после входа, могут взаимно отозвать токен друг друга и выкинуть на `/login`. Single-flight есть в пределах одной вкладки (`client.ts`), но не между вкладками. Чинится grace-period в backend или переходом на cookie-сессию без ротации — это зона Dev B (auth/2FA). |

## 5. Как воспроизвести

```bash
cd frontend && npm run build
# прод-бандл за nginx-подобным статик-сервером на 5176 с прокси на :8080
cd /tmp/gusto-audit && node crawl.mjs     # обход + клики + ошибки + переполнение
cd /tmp/gusto-audit && node design.mjs    # бренд + WCAG
cd /tmp/gusto-audit && node tap.mjs       # тап-таргеты на 375px
```

Обязательно `docker exec gusto-b2b-redis-1 redis-cli flushall` перед прогоном —
лимит 5 попыток входа на 15 минут на email.
